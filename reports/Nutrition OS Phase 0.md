# Nutrition OS can start with meals

Phase 0 feasibility report · October 26, 2026

**Begin Phase 1 with a new private Google Sheet and a synthetic meal-logging test in Scout’s actual ChatGPT environment.** This Codex session exposes native tools for creating, reading and updating Sheets; read-only access to an existing workbook succeeded, but meal writes and corrections remain untested. Garmin documents a Personal API suitable for individual weight access. TrainingPeaks offers a limited Premium calendar feed, with weekly coach-plan import as a simpler fallback. Strava’s API supplies the requested activity fields, but current usage restrictions require clarification before approving the proposed storage and analysis workflow. Keep Nutrition OS independent of Colorado Compass and Air Quality. No production code, credentials, external services or new workbook were created.

## Native Sheets is the first integration gate

Evidence labels below distinguish **E: verified through execution**, **D: verified in official documentation**, and **U: unverified**. Advertised connector operations are separately identified: a tool schema proves availability in this session, not successful execution or availability in Scout’s intended chat.

| Integration | Compatibility and evidence | Authentication and permission | Phase 1 decision |
|---|---|---|---|
| Scout ↔ Google Sheets | **E:** narrow Drive search and existing Air Quality workbook metadata read succeeded, without reading sensor cells. Tool inventory advertises native workbook creation, bounded cell reads, ID search and batch updates. **D:** Google supports `appendCells` and `updateCells`. **U:** new workbook, meal append/readback/correction, write permission, Scout’s runtime. | Existing personal Google OAuth connection; inspect its actual consent and file permissions. A connector in Codex does not establish access in another chat or mobile context. | Native connector first. Test the complete loop before routine logging. |
| Strava → Sheets | **D:** completed activity list/detail endpoints supply required fields; current policy introduces storage/analysis and downstream AI questions. **U:** account authorization, allowed project use and actual responses. | Registered application, Strava subscription to create it, athlete OAuth; `activity:read_all` for Only Me activities. Secure client secret and rotating refresh token. | Defer ingestion pending clarification of intended use. |
| Garmin Index → Sheets | **D:** Personal API for individuals, token exchange and weight-history endpoints. **U:** account access, Index provenance and body-composition fields. | User-generated expiring Personal API key; exchange for 24-hour bearer token, without refresh tokens. | Validate one known weigh-in; initially import weight only. |
| TrainingPeaks → Sheets | **D:** personal API access excluded; Premium ICS subscription exposes 14 future days and 5 past days, with changes taking up to 24 hours. **U:** direct feed ingestion and actual field completeness. | Premium entitlement plus private subscription URL; no partner OAuth needed for fallback. | Start with weekly future-plan copy/import; use ICS only if useful and validated. |

Google’s batch update supports ordered, validated requests and responses, but **confirmation should include a separate read of persisted values**. Create a dedicated Food log tab without footer content; locate corrections by stable ID, freshly read the row, then update its precise cells. Google scopes apply to the whole spreadsheet, not individual tabs. Prefer the existing personal OAuth connection; inspect requested scopes rather than promising that this connector uses a particular narrow scope. [Google requests](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/request), [batch updates](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/batchUpdate), [authorization scopes](https://developers.google.com/workspace/sheets/api/scopes).

The necessary tools are present in **this Codex environment**. Whether Scout’s intended ChatGPT chat, configured assistant, voice/photo flow and mobile surface expose those same tools and permissions remains unverified. That distinction is the highest-priority acceptance gate. Apps Script is a fallback only if native access or retry behavior fails the test, not an initial dependency.

## Provider access is feasible, with separate usage gates

**Strava → Sheets and Sheets → Scout are separate decisions.** Sending data to a Sheet does not itself establish that it is sent to an AI assistant. If Scout subsequently reads those cells or derived summaries, however, that becomes downstream AI use. Strava’s June 2026 policy §5.3 addresses AI use including context ingestion and derived data; §§5.4–5.5 also contain broad analytics, data-combination and persistent-retrieval restrictions. These create questions for private Sheets storage and nutrition analysis even without an immediate AI read. This report does not make a categorical legal determination about private storage. Obtain clarification for the specific personal workflow before implementation; a Sheet or derived summary does not by itself resolve the restrictions. The documented personal MCP exception is separate, and the September FAQ describes a Claude launch, not a verified ChatGPT route. [Strava API policy](https://www.strava.com/legal/api_policy), [API agreement](https://www.strava.com/legal/api), [API and MCP FAQ](https://support.strava.com/en-us/articles/15401526-strava-api-and-mcp-faq).

Technically, `GET /athlete/activities` supports timestamp windows and pagination; `GET /activities/{id}` provides details. Store activity ID as text, `sport_type`, UTC start, moving/elapsed seconds, meters, estimated kilocalories and optional heart rate, power and energy metrics. Missing calories or intensity stays null; mechanical kilojoules are not nutritional calories. Apps initially support one athlete. Default read limits are 100 requests per 15 minutes and 1,000 daily; honor actual response headers. [Getting started](https://developers.strava.com/docs/getting-started/), [API reference](https://developers.strava.com/docs/reference/), [rate limits](https://developers.strava.com/docs/rate-limits/).

If permitted, a small scheduled job can paginate a rolling overlap window, fetch details and upsert by Strava activity ID, with periodic reconciliation for older edits. Serialize runs; update the success watermark only after verified writes. Deletions, privacy changes and revoked access need explicit handling; a missing record alone is not proof of deletion. Access tokens last six hours and refresh tokens rotate: an initial GitHub secret without a secure mechanism to persist replacements is insufficient. Choose that mechanism explicitly during implementation. Strava remains the **only completed-workout source**, across all activity types. [Authentication](https://developers.strava.com/docs/authentication/), [webhook event semantics](https://developers.strava.com/docs/webhooks/).

Garmin’s **Personal API is distinct from its business Health API**. Individuals generate a key in Garmin Connect, choose an expiry and exchange it for a 24-hour bearer token; refresh tokens are unsupported. Documented weight endpoints include `/weight-service/weight/all/{startDate}/{endDate}` and `/weight-service/weight/range/{startDate}/{endDate}`; Garmin’s own Python client supports the range call with `includeAll=true`. A fresh token per daily run avoids rotating-refresh-token storage. Exact payload fields, units, measurement IDs, timestamps, history limits, quotas and account eligibility remain untested. [Personal API FAQ](https://developer.garmin.com/gc-developer-program/personal/personal-faq/), [instructions](https://developer.garmin.com/gc-developer-program/personal/personal-api/), [reference](https://developer.garmin.com/gc-developer-program/personal/swagger-docs), [official client](https://github.com/garmin/connect-personal-api-python).

Do not promise automatic body fat, water, muscle or bone mass until a known Index record proves those fields. Connect can contain manual and other-source weigh-ins, so preserve available provenance rather than labelling every record Index-derived. Impedance body-composition values remain estimates. The supported fallback is periodic Connect weight CSV export, then import, or a manually transcribed weigh-in. Import no Garmin activities. [Weight data FAQ](https://support.garmin.com/en-US/?faq=zS4yMMr7REAVHBPYY6DaZ5), [export instructions](https://support.garmin.com/zh-HK/?faq=W1TvTPW8JZ6LfJSfK512Q8).

TrainingPeaks explicitly excludes personal API use. Its supported Premium calendar subscription has a bounded horizon and delayed updates; direct ICS → Sheets processing still needs validation of fields, permissions and refresh behavior. Keep only future coach-prescribed workouts, retain all-day dates without inventing times, and distinguish a cancellation from an event aging out of the feed window. If duration or intensity is absent, use coach text or unknown. Weekly copy/paste of the next seven days is adequate initially. [API restrictions](https://help.trainingpeaks.com/hc/en-us/articles/234441128-TrainingPeaks-API), [calendar subscription](https://help.trainingpeaks.com/hc/en-us/articles/204072184-Sync-your-calendar).

## One independent directory and eight tabs suffice

**Repository inspection, verified through execution:** Colorado Compass is a static root application (`index.html`, `assets/`, `CNAME`). Air Quality is independently organized under `side-projects/dyson-air-quality/`, `tempest-air-quality/`, `air-quality-analysis/` and `air-quality-google-apps-script/`; `home-air-quality/` contains separate informational pages. The Apps Script project has configuration/utilities, Sheets storage, orchestration and source modules. Its upserts, locks and Denver-date handling offer design examples, not a shared library to import.

Existing GitHub workflows include manual smoke tests and six-hour Dyson/NCAR collection, with concurrency controls, timeouts and secret references. Credentials use environment/Keychain, ignored local files, Actions Secrets and Apps Script Properties. Existing Apps Script permissions are broader than Nutrition OS needs; do not copy that grant. Per-project README files cover setup, security, data semantics, tests and limitations; root DEVLOG covers the app. Repository documentation identifies it as public, but live hosting, secrets and deployments were not inspected. [Repository README](../README.md), [Air Quality integration README](../side-projects/air-quality-google-apps-script/README.md), [workflows](../.github/workflows), [ignore rules](../.gitignore).

Recommend root **`nutrition-os/`**, with its own README, eventual scripts/tests and explicitly scoped workflows, on short-lived **`nutrition-os/phase-1-foundation`** after review. No branch was created. Reuse patterns, not deployments, credentials, spreadsheets or production modules. Keep personal data outside git, logs and artifacts. GitHub Actions is conditional scheduled ingestion, not a new backend; no dashboard, database or shared-library extraction is needed.

The new private spreadsheet is the sole store. The following is a proposed schema, not an implemented workbook. Shared mutable-row fields are `id`, `source`, `source_id` when supplied, `recorded_at_utc`, `updated_at_utc`, `revision`, `status` and `correction_reason`. Preserve original source timestamp/date and its precision; derive reporting dates in **America/Denver**, including DST. Never fabricate UTC time for a date-only record. Use explicit units and null for unknown values.

| Tab | Minimum fields beyond shared provenance/correction fields |
|---|---|
| Food log | `meal_id` (row ID), `operation_id`, `consumed_at_utc` nullable, `local_date`, `time_precision`, `meal_type`, description, quantity/unit, `quantity_method`, kcal, protein_g, carbohydrate_g, fat_g, `nutrition_basis` |
| Daily nutrition targets | `target_id`, `local_date` unique, kcal/protein/carbohydrate/fat targets, target rationale/source; user-approved values, initially nullable |
| Completed activities | `activity_id` from Strava as text, start UTC, Denver date, sport, moving_s, elapsed_s, distance_m, estimated_kcal, optional HR/power/kJ, `device_watts`, `last_seen_at_utc` |
| Planned workouts | `plan_id`, source UID or manual ID, planned date, optional start UTC, time precision, sport, title, planned duration_s, coach intensity/description, source revision, `last_seen_at_utc` |
| Body metrics | `measurement_id`, source timestamp/date, Denver date, weight_kg, nullable body_fat_pct/other validated fields with units, device/source detail, measurement method |
| Daily summary | `local_date` key, active food totals, target differences, logging completeness, latest weight, optional permitted activity totals, source freshness; derived values only |
| Weekly summary | Monday `week_start_local_date` key, logged-day count, nutrition averages, weight trend/sample count, permitted activity totals, source freshness; derived values only |
| Settings | `setting_key` unique, value, updated timestamp; timezone, units, week start, source enablement, last successful sync and last error category; **no secrets** |

A weighed quantity does not make model-estimated nutrients measured: distinguish `quantity_method=weighed/reported/photo_estimate` from `nutrition_basis=label/database/model_estimate`. Maintain one canonical food row, increment revision for correction and mark void rather than deleting silently. Preserve `meal_id` and `operation_id` across retries, search before append and reconcile after timeouts. Native search-then-append is not an atomic uniqueness guarantee: initially use one food writer and serialize actions. Investigate a separately authenticated Apps Script intake with locking only if concurrency demands it. Summaries must distinguish incomplete logs from zero intake and must not automatically add exercise calories to targets.

## Validate the smallest loop before automation

The implementation sequence after review is: establish the independent directory/branch and private workbook; run synthetic creation, append, read, correction and retry tests in Scout’s intended runtime; enable routine food logging and simple summaries; validate weight import; add weekly future coach plans; add scheduled ingestion only for validated sources. Keep Strava disabled until its usage gate is resolved. Every write must read back matching ID, revision and intended values before Scout says “logged”; ambiguous results remain unconfirmed and trigger reconciliation.

Necessary tests are a corrected synthetic meal leaving exactly one active row; timeout/retry without duplication; concurrent-chat behavior; denied permissions and unavailable tools; weighed-versus-estimated provenance; incomplete-day summaries; Denver midnight/DST and date-only handling; known Index reading/unit comparison and repeated-import deduplication; coach plan edit/move/removal and feed-window expiry. Conditional Strava tests cover all sport types, pagination, missing metrics, edits/deletions/privacy, 401/429 handling, token rotation across runs and partial-write recovery. Scheduled jobs need sanitized errors, no health payload artifacts, serialized runs and visible freshness. **Only read-only connector access and repository inspection were executed in Phase 0; these acceptance tests remain unexecuted.**

Expected infrastructure cost is low: no new hosting or database. Existing Sheets/ChatGPT entitlements and intended-runtime tool access must be checked. Actions cost depends on plan, repository visibility and usage. Garmin Personal API pricing and quotas were not published in the inspected sources, so do not guarantee free access. Strava requires a subscription for app creation; exact localized incremental cost is unverified. TrainingPeaks publicly lists $19.95/month or $134.99/year; avoid buying Premium solely for calendar import if weekly copying suffices. [TrainingPeaks pricing](https://www.trainingpeaks.com/pricing/for-athletes/).

**Review point:** approve the meal-loop validation as the first Phase 1 scope, with Garmin and coach-plan additions gated by sample checks. External provisioning, credentials and production implementation remain deferred pending review.
