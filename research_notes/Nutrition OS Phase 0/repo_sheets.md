## Can the native connector support the meal logging loop?

### Takeaway
The Google Drive plugin actually exposed in this Codex session advertises all necessary primitives. Read-only Drive search and live spreadsheet metadata retrieval succeeded for the existing Air Quality workbook. Dedicated Nutrition workbook creation, append, correction and write confirmation remain unverified because Phase 0 prohibits external provisioning without approval. Native connector first; Apps Script is not currently necessary.

### Cited Findings
- **Verified through execution:** `google_drive_search` narrowly queried Air Quality spreadsheets and returned the private Air Quality workbook; `google_drive_get_spreadsheet_metadata(charts_only=true)` succeeded and returned its tab metadata, including README, Schema and Master_15min. No sensor cells were read and no external data changed. Workbook IDs deliberately omitted from notes. Source: actual tool execution in this research session, 2026-10-26.
- **Verified by tool inventory, not write execution:** `google_drive_create_file` accepts native Sheets MIME type; `google_drive_batch_update_spreadsheet` accepts raw Sheets requests; `get_spreadsheet_range`/`get_spreadsheet_cells` provide bounded reads; `search_spreadsheet_rows` can locate IDs in bounded ranges (50,000-cell scan ceiling). This establishes usable tools advertised in this environment, not account write permission. Source: actual session tool schemas inspected 2026-10-26.
- **Verified in official documentation:** Sheets requests include appendCells and updateCells. appendCells inserts after the last populated row; use a dedicated tab with no footer data. updateCells targets ranges; field masks matter, and an oversized range can clear cells. [Google request reference](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/request).
- **Verified in official documentation:** batchUpdate validates requests first, processes in order and returns replies plus optional updated spreadsheet. Use a separate read after success to validate persisted ID/revision/values; a generic success message alone is insufficient operational confirmation. [Google batchUpdate](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/batchUpdate).
- **Verified in official documentation:** OpenAI plugins work across supported Chat and Work surfaces including mobile, and Codex desktop. Google Drive covers Docs/Sheets/Slides; available tools and permissions remain contextual to the chat/account. [OpenAI plugins](https://learn.chatgpt.com/docs/plugins).
- **Verified in official documentation:** Google connection uses the approved account and its file permissions; read and write permissions should be checked separately. Direct service accounts, where offered, require a writable shared drive to create files and cannot own personal My Drive files. Prefer the existing personal OAuth connection for a personal Sheet. [OpenAI workspace connections](https://learn.chatgpt.com/docs/enterprise/shared-connections).
- **Verified in official documentation:** Sheets scopes apply at spreadsheet level, not individual tabs. Google recommends narrow `drive.file` when possible; `spreadsheets` is broader. The installed connector decides requested scopes, so inspect its consent rather than promising a custom scope. [Google scopes](https://developers.google.com/workspace/sheets/api/scopes).

### Inferences
- Compatibility table: create/access = access executed, new creation advertised/unverified; append = advertised via appendCells/unverified; readback = metadata executed, meal cell read unverified; correction = advertised via ID lookup+updateCells/unverified; confirmation = response+read primitives available/unverified write loop.
- First Phase 1 gate must run in Scout's actual intended ChatGPT chat/mobile context, with same plugin/account: create NEW private workbook, append synthetic meal with generated meal_id and operation_id, read it, correct same ID with revision increment, read again and confirm only one active meal. Codex success is not proof of Scout's configured GPT/chat, voice path, mobile experience or its write permissions.
- Keep one canonical row per food entry; generate meal_id before first attempted write and preserve it across retry. Search exact ID before append and after any timeout. Corrections locate by stable ID, freshly read row/revision then update in place; never store row number as identity. Use status=void for deletion. updated_at, revision, correction_reason retain minimal correction provenance; Sheets revision history can supplement, not replace structured flags.
- Native search-then-append is not an atomic unique-key transaction. Phase 1 should use a single food writer and serialize actions, then test ambiguous retry; do not claim hard duplicate prevention across simultaneous chats. If concurrency or actual write limitations prove unacceptable, investigate a separate minimal Apps Script intake with ScriptLock and idempotent operation IDs, explicit authentication and readback. Do not deploy an anonymous unauthenticated write endpoint or reuse AQ intake.
- Never tell user “logged” until readback matches meal_id, revision and intended values. On unavailable tools, permission failures or ambiguous outcome, say pending/unconfirmed and reconcile ID before retrying. Preserve data in Sheet rather than conversational memory.
- Store quantity basis separately from nutritional estimate basis: weighed food does not make model-inferred calories measured. Fields such as quantity_method=weighed/reported/photo_estimate and nutrition_basis=label/database/model_estimate avoid conflation. Source/provenance, units, UTC recorded timestamps, Denver reporting dates and date/time precision should be explicit.

### Gaps
- No dedicated workbook or credentials created; no append/update/correction executed. Account scopes, create/write permission and end-to-end behavior in Scout's actual chat remain unknown. Connector availability does not establish reliability of natural-language, voice or photo logging. No new subscriptions required by this design; exact account entitlement must be verified in intended runtime.
